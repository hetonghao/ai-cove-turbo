# AI Cove Turbo MVP 规格

## Problem Statement

Codex 在使用自定义 API Key Provider 时，原生请求压缩受内部条件限制，不能仅靠配置稳定获得请求体压缩；而 `/v1/responses` 的 WebSocket 模式还要求 Provider 明确声明支持，并依赖上游真正接受 WebSocket Upgrade。用户目前需要手动运行本地代理、修改 Codex 配置、处理端口冲突、重启 Codex Desktop、判断配置是否真正生效，并在退出时恢复原配置。这套流程容易出错，也无法让普通用户稳定获得压缩和连接复用带来的收益。

用户需要一个跨 macOS 与 Windows、低存在感、可随系统启动的桌面应用，在不接触 API Key 和请求正文的前提下接管当前 Codex Provider 的连接配置。应用应默认启用压缩模式和 WebSocket 模式，允许两者独立开关，能识别配置写入、桌面应用重启、真实请求验证之间的差异，并在正常退出或异常恢复时尽量把 Codex 配置还原到接管前状态。

## Solution

构建 AI Cove Turbo：一个基于 Tauri 2 和 Rust 原生核心的常驻桌面应用。Turbo 在本机回环地址启动轻量请求通道，按用户开关对 Codex HTTP JSON 请求进行 zstd 压缩，并透明转发 Responses WebSocket 连接。Turbo 只接管根 `model_provider` 指向的受管 Provider，只修改其连接端点与 WebSocket 支持标记，不修改 Codex 原生请求压缩功能。

Turbo 首次启动默认开启压缩模式、WebSocket 模式和开机自启动。它在本地服务真正监听成功后才更新 Codex 配置，端口冲突时自动选择空闲端口；用户关闭窗口时继续后台运行，明确退出时恢复仍由 Turbo 持有的配置字段。应用通过运行状态、配置状态、Codex Desktop 重启状态和实际请求观测，向用户说明功能是否真正生效，并在需要时提供只重启 Codex Desktop 的操作。

Turbo 以 AI Cove 为主要兼容上游。用户可以继续使用其他 HTTPS 上游，但界面必须持续提示其配置可能不生效或产生错误。首版记录当前运行周期的聚合传输指标，不保存请求正文、响应正文、API Key、完整请求头或历史数据库。后续通过受控 A/B 基准测试校准节省流量与时间的估算模型。

## User Stories

1. 作为 Codex 用户，我希望 Turbo 自动启动本地加速通道，以便不再手动运行网关脚本。
2. 作为首次使用者，我希望压缩模式默认开启，以便无需先理解传输细节就能获得核心收益。
3. 作为首次使用者，我希望 WebSocket 模式默认开启，以便上游能力可用后应用已经处于就绪状态。
4. 作为用户，我希望压缩模式和 WebSocket 模式是独立开关，以便可以只开一个、两个都开或两个都关。
5. 作为用户，我希望关闭压缩模式时保留 WebSocket 模式，以便修改一个能力不会意外改变另一个能力。
6. 作为用户，我希望关闭 WebSocket 模式时保留压缩模式，以便 HTTP 上传仍能压缩。
7. 作为用户，我希望 Turbo 自动定位默认 Codex 配置，以便正常使用时不需要选择路径。
8. 作为缺少默认 Codex 配置的用户，我希望看到明确的阻塞错误，以便 Turbo 不会擅自创建或静默修复 Provider。
9. 作为配置 TOML 损坏的用户，我希望 Turbo 在接管前停止，以便现有配置不会进一步受损。
10. 作为缺少根 Provider 选择的用户，我希望获得可操作的错误提示，以便修正 Codex 后重试。
11. 作为缺少已选 Provider 定义的用户，我希望获得可操作的错误提示，以便 Turbo 不会修改无关 Provider。
12. 作为配置了多个 Provider 的用户，我希望 Turbo 只管理根配置选中的 Provider，以便其他 Provider 保持不变。
13. 作为用户，我希望 Turbo 只修改受管 Provider 的端点和 WebSocket 支持字段，以便其他 Codex 设置保留原意。
14. 作为用户，我希望 Turbo 不写入 Codex 原生请求压缩功能键，以便不引入不受支持或会误导用户的配置。
15. 作为用户，我希望 Turbo 接管前保存受管字段原值，以便退出时恢复。
16. 作为用户，我希望明确正常退出时恢复受管字段，以便 Turbo 不可用时 Codex 回到原路径。
17. 作为经历 Turbo 异常退出的用户，我希望下次启动自动识别并修复残留接管状态，以便不会一直指向失效的本地端点。
18. 作为运行期间手动修改 Codex 配置的用户，我希望外部修改取得字段所有权，以便 Turbo 不覆盖我的意图。
19. 作为遇到配置冲突的用户，我希望 Turbo 说明哪个受管字段被外部修改，以便有意识地处理冲突。
20. 作为用户，我希望 Turbo 原子更新 Codex 配置，以便写入期间崩溃不会留下半份文件。
21. 作为用户，我希望 Turbo 只绑定回环地址，以便本地通道不会暴露给局域网。
22. 作为用户，我希望 Turbo 尽量复用上次成功端口，以便多次启动之间端点保持稳定。
23. 作为用户，我希望端口冲突时 Turbo 无感切换空闲端口，以便不结束无关进程也能继续启动。
24. 作为用户，我希望监听和健康检查成功后才写本地端点，以便 Codex 不会被路由到不可用服务。
25. 作为发送 JSON 请求的用户，我希望仅在请求符合条件且压缩后更小时使用 zstd，以便压缩不会反而浪费流量。
26. 作为发送已编码请求的用户，我希望 Turbo 保留现有编码，以便请求不会被重复压缩。
27. 作为使用流式响应的用户，我希望 SSE 数据逐步透传，以便 Turbo 不增加整段缓冲延迟。
28. 作为用户，我希望认证、模型和 AI Cove 自定义请求头被安全转发，以便保持上游兼容行为。
29. 作为用户，我希望 hop-by-hop 头被正确过滤，以便单跳连接状态不会跨代理传播。
30. 作为发送超大请求体的用户，我希望 Turbo 按明确上限拒绝请求，以便本地请求不能无限消耗内存。
31. 作为使用 Responses WebSocket 的用户，我希望 Turbo 透明转发 Upgrade 和数据帧，以便 Codex 无需自定义协议即可使用上游连接模式。
32. 作为使用 WebSocket 压缩的用户，我希望保留标准 `permessage-deflate` 协商，以便 Turbo 不引入私有 zstd 帧格式。
33. 作为 WebSocket 尝试后回退 HTTP 的用户，我希望回退请求仍可使用 zstd，以便一个模式失败不会关闭另一个模式。
34. 作为 AI Cove 用户，我希望标准 AI Cove 端点被识别为主要受支持上游，以便兼容状态明确。
35. 作为使用其他 HTTPS 上游的用户，我希望 Turbo 提示风险但允许继续测试，以便理解风险同时保留控制权。
36. 作为当前 Provider 已指向回环地址的用户，我希望 Turbo 拒绝将该地址导入为上游，以便避免代理回环。
37. 作为重视安全的用户，我希望 Turbo 只透传认证信息而不保存 API Key，以便应用不会成为新的密钥存储点。
38. 作为用户，我希望区分本地服务健康和 Codex 配置状态，以便不会把 Turbo 进程正常误认为 Codex 已经走新路径。
39. 作为用户，我希望区分配置已写入和 Codex Desktop 已重启，以便判断运行中的应用是否仍持有旧配置。
40. 作为用户，我希望每项加速能力只在观察到匹配真实请求后标记已验证，以便 Turbo 不会仅凭配置宣称成功。
41. 作为尚未发起请求的用户，我希望看到“等待首次请求验证”，以便缺少证据不会被显示成故障。
42. 作为 Codex Desktop 仍使用旧配置的用户，我希望一键重启桌面应用，以便无需手动管理进程即可加载新 Provider 配置。
43. 作为用户，我希望重启动作只影响 Codex Desktop，以便 CLI、MCP 和独立 app-server 不被中断。
44. 作为 macOS 用户，我希望 Turbo 主要驻留菜单栏并默认隐藏 Dock 图标，以便工具保持低存在感。
45. 作为 macOS 用户，我希望能在设置中显示 Dock 图标，以便需要时使用传统应用入口。
46. 作为 Windows 用户，我希望 Turbo 主要驻留系统托盘，以便窗口隐藏时不占用任务栏。
47. 作为用户，我希望关闭设置窗口只隐藏而不停止加速，以便窗口操作不会打断 Codex 流量。
48. 作为用户，我希望有明确的“退出 Turbo”命令，以便停止服务和恢复配置是有意识的操作。
49. 作为首次使用者，我希望开机自启动默认开启，以便重启系统后 Codex 不会指向未运行的本地端点。
50. 作为用户，我希望能关闭开机自启动，以便保留对后台启动的控制权。
51. 作为用户，我希望在同一处看到当前上游、本地端点和兼容性警告，以便快速理解真实路由。
52. 作为用户，我希望看到当前运行周期的请求数和字节数，以便确认 Turbo 正在处理流量。
53. 作为用户，我希望看到原始字节、转发字节和压缩率，以便流量收益基于真实观测。
54. 作为用户，我希望看到 WebSocket 握手和 HTTP 回退次数，以便理解 Codex 实际使用了哪种传输。
55. 作为重视隐私的用户，我希望运行指标排除正文、密钥和完整请求头，以便监控不会留存敏感内容。
56. 作为重视隐私的用户，我希望退出后清空运行指标，以便 MVP 不创建历史流量数据库。
57. 作为用户，我希望真实指标与估算收益明显分开，以便模型结果不会被呈现为精确观测。
58. 作为产品运营者，我希望 HTTP 收益按减少字节、上行速度和压缩 CPU 时间校准，以便未来估算符合真实网络条件。
59. 作为产品运营者，我希望 WebSocket 收益按请求轮次、RTT、连接复用、TLS 建连和回退行为校准，以便不会错误地把 token 直接换算成时间。
60. 作为发布人员，我希望 macOS arm64 和 Windows x64 分别在原生 Runner 构建，以便平台打包可复现。
61. 作为用户，我希望 Turbo 安装前验证更新签名，以便篡改过的安装包被拒绝。
62. 作为用户，我希望看到更新下载进度和明确的重启步骤，以便理解更新过程。
63. 作为发布人员，我希望从 AI Cove 下载域名发布合并后的更新清单，以便客户端使用稳定的正式更新源。
64. 作为发布人员，我希望 Turbo 使用独立更新签名密钥，以便密钥泄露或轮换不影响其他 AI Cove 桌面产品。
65. 作为开发者，我希望在 AI Cove 开启生产 WebSocket 前，先用本地模拟上游验证 Turbo 转发，以便客户端开发可以独立推进。
66. 作为开发者，我希望最终 WebSocket 端到端验证同时以 Turbo 和 AI Cove 支持完成为门禁，以便本地成功不会被误报为生产可用。

## Implementation Decisions

- 桌面应用使用 Tauri 2、Rust 原生核心和系统 WebView；界面使用简单 HTML、CSS、JavaScript，不携带 Electron 或 Node 运行时。
- 首发平台为 macOS Apple Silicon 与 Windows 10/11 x64；Intel Mac 和 Windows ARM64 不在首版范围内。
- Rust 核心负责本地 HTTP 代理、zstd 压缩、WebSocket 透传、Codex 配置接管、进程生命周期集成、运行指标和更新集成。
- 应用主要以 macOS 菜单栏或 Windows 托盘形态存在。关闭设置窗口只隐藏；明确退出才恢复配置并停止本地服务。
- 首次启动默认开启压缩模式、WebSocket 模式和开机自启动；压缩和 WebSocket 始终保持独立控制。
- Turbo 只读取当前用户的默认 Codex 配置位置。文件缺失、不可读、无法解析或 Provider 不完整时，以可操作错误阻止接管。
- Turbo 只管理根 `model_provider` 选中的 Provider，受管字段仅限 `base_url` 和 `supports_websockets`。
- Turbo 不修改 Codex 原生请求压缩功能键。
- 受管字段采用所有权感知恢复。Turbo 只恢复仍由自己持有的值；外部修改会产生冲突并把字段所有权交给外部编辑者。
- 配置更新保留当前文件中的无关内容，并使用临时文件加原子替换。
- 使用最小恢复记录区分接管状态和原始受管值。启动时先处理上次异常退出留下的残留状态，再开始新一轮接管。
- 本地监听只绑定回环地址，依次尝试上次成功端口、产品默认端口和操作系统分配的空闲端口。
- 只有绑定和健康检查成功后，才把 Codex 指向本地端点。
- 默认上游是 AI Cove API。其他 HTTPS 上游允许在持续警告和首次确认后使用。
- 回环地址不能作为导入上游，以免 Turbo 把请求转发回自身。
- HTTP 压缩只针对符合条件、尚未编码的 JSON 请求体，并且仅在 zstd 结果更小时启用；初始压缩等级为 3。
- MVP 请求体上限为 128 MiB。
- 认证、模型选择和 AI Cove 端到端自定义头会被转发；hop-by-hop 头按出站协议过滤或重建。
- SSE 响应逐步流式透传，不做整段缓冲。
- Responses WebSocket 透明转发，并保留标准 `permessage-deflate` 协商；不定义自定义 WebSocket zstd 帧格式。
- HTTP 回退路径仍独立支持请求体 zstd 压缩。
- Turbo 不把 API Key 作为应用配置读取或持久化，认证信息只随请求透传。
- 运行状态分别表示本地服务可用、配置写入完成、Codex Desktop 已重启、HTTP 压缩已验证和 WebSocket 已验证。
- 只有观察到匹配的真实请求后，功能才标记为已验证；此前界面显示中性的等待状态。
- 重启动作只针对可识别的 Codex Desktop，使用平台适配的优雅退出和重新打开机制，不按宽泛进程名结束进程。
- 运行遥测只保存在内存并且只记录聚合值：请求数、原始与转发字节数、压缩率、WebSocket 握手状态、HTTP 回退次数。它不记录正文、API Key 或完整请求头。
- MVP 展示真实流量指标，但不展示未经校准的节省时间估算。
- 后续 HTTP 收益估算使用减少字节、实测上行条件和压缩 CPU 成本；WebSocket 估算使用请求轮次、RTT、连接复用、TLS 建连和回退频率，token 数只作为工作负载特征。
- 更新使用 Tauri 签名更新流程。Turbo 使用独立签名密钥，并从 AI Cove 下载域名读取合并后的更新清单。
- 发布流程复用现有原生 macOS/Windows Runner、平台产物收集、清单合并和发布校验方案。CI Artifacts 只用于构建交付和备份，不作为正式更新源。
- AI Cove 上游 WebSocket 能力在本项目外交付。Turbo 先使用本地模拟上游验证透明转发，待上游能力完成后再做生产端到端集成。

## Testing Decisions

- 测试只断言外部可观察行为，不绑定内部函数结构。高质量测试从三个最高层 seam 之一进入，观察配置、网络、进程或更新包结果。
- 配置接管与恢复 seam 覆盖默认路径发现、解析失败、Provider 选择、最小字段修改、原子写入、正常恢复、残留状态修复和外部编辑冲突。
- 本地 HTTP/WebSocket 代理 seam 覆盖回环绑定、动态端口、健康后写配置、可压缩与不可压缩请求、zstd 行为、请求体上限、header 转发、hop-by-hop 过滤、SSE 流式透传、WebSocket Upgrade 与字节透传、`permessage-deflate` 保留和 HTTP 回退。
- 桌面生命周期与更新 seam 覆盖首次启动默认值、托盘/菜单栏行为、隐藏窗口与退出的区别、开机自启动、Dock 可见性、Codex Desktop 检测与安全重启、更新清单解析、签名拒绝、下载/安装进度、应用重启和跨平台打包。
- 配置测试使用临时用户目录和代表性 TOML fixture，检查最终文件和恢复状态，不测试私有解析辅助函数。
- 代理测试使用本地 HTTP、SSE、WebSocket 模拟上游，从公共监听入口发请求，并观察两端真实字节与 header。
- 进程生命周期测试使用平台适配器或可控模拟应用，证明只操作 Codex Desktop，不结束真实用户进程。
- 运行指标测试通过公共代理发送已知流量，验证聚合计数，并断言持久化状态中不存在敏感正文。
- 更新测试使用正确签名和被篡改的清单及产物，从更新边界验证接受或拒绝行为。
- 平台验证包含 macOS arm64 本地原生构建、Windows x64 CI 原生构建，以及产物和合并更新清单的完整性校验。
- WebSocket 交付分两道门禁：本项目先通过本地模拟上游验收；上游实现完成后，再执行真实 AI Cove 端到端测试。
- 现有 AI Cove 压缩网关和 Tauri 桌面发布流程作为行为参考，但 Turbo 测试针对自身公开 seam 编写，不复制实现细节测试。

## Out of Scope

- 修改 AI Cove 服务端的 Responses WebSocket 实现。
- 修改 Codex 源码或在 Codex 内部绕过认证门禁。
- 设置或依赖 Codex 原生请求压缩功能键。
- 同时管理多个 Provider，或扫描任意 Codex 配置目录。
- 自定义配置文件选择器、自动创建 Provider、自动修复损坏的用户 TOML。
- 把本地服务绑定到局域网或公网接口。
- 结束占用首选端口的未知进程。
- 自定义 WebSocket zstd 帧或标准协商之外的协议扩展。
- 持久化请求历史、记录流量正文、保存 API Key 或建立历史指标数据库。
- 在基准校准前宣称精确节省时间。
- 在 MVP 中实现公开付费发布就绪、Intel Mac、Windows ARM64 或 Linux 打包。
- 在桌面应用未运行时仍保证恢复的后台系统服务。
- 重启 Codex CLI、MCP Server、独立 app-server 或无关进程。
- 不经过正式实现阶段，直接把一次性 UI 原型提升为生产代码。

## Further Notes

- 产品名称是 AI Cove Turbo；早期使用的 “Turbine” 名称已废弃。
- 计划中的正式更新清单地址是 `https://ai-cove.com/downloads/turbo/latest.json`。
