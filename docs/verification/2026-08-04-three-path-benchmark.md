# Turbo 3×3 基准测试

## 目标

本基准比较 3 类使用场景 × 3 类技术路径，而不是把一个 HTTP POST 和一条 WebSocket 应用消息当成等价样本。

### 使用场景

| 场景 | 负载 | 逻辑请求数 |
|---|---|---:|
| 单轮短上下文 | 固定短提示词，观察小包被 zstd envelope 放大或不压缩的真实情况 | 1 |
| 单轮长上下文 | 默认约 20 KB 的重复/结构化上下文，可由 `TURBO_BENCHMARK_PROMPT` 覆盖 | 1 |
| 连续多轮会话 | 同一工作负载连续 5 轮，每轮带轮次标记和长上下文 | 5 |

### 技术路径

| 路径 | 真实行为 |
|---|---|
| 直连（不走 Turbo） | 每个逻辑请求直接 HTTP POST 到 AI Cove |
| Turbo HTTP + zstd | 每个逻辑请求独立 HTTP POST，经 Turbo 压缩请求体 |
| Turbo WS + zstd | 每个场景样本只建立一次 WebSocket，随后逐轮发送 `response.create`，经 `ai-cove-zstd.v1` 传输 |

因此最终输出 9 个单元格。WS 的服务端响应事件不是用户请求；报告分别列出逻辑请求、应用消息、响应事件和 WebSocket 握手数。

## 计时和字节口径

- `总 E2E`：从场景第一轮开始到最后一轮完整响应结束。WS 包含一次握手。
- `每轮 E2E`：每轮发送应用消息到该轮 `response.completed` 或 `response.done` 的耗时；不包含初始 WS 握手。
- `总传输`：场景内所有 HTTP 请求体或 WS 应用帧完成交给发送器的耗时之和。HTTP 是请求体流交给 reqwest 发送器的边界，WS 是 `send()` 完成边界；不宣称网卡 flush，也不包含响应下载和模型推理。
- `每轮传输`：单轮发送边界的统计，便于观察连接复用后的每轮成本。
- `WS 握手`：每个正式样本一次，只在 WS 路径单列，并且已经包含在总 E2E 中。
- `raw → wire`：只统计应用负载，不包含 HTTP/WS 头、TLS、TCP/IP 头；Turbo 路径来自实际运行指标，直连路径 wire 等于 raw。
- `响应事件`：HTTP 统计 SSE `data:` 行，WS 统计收到的文本/二进制数据消息；这是事件量指标，不把它解释成用户请求数。

这仍不是网卡级抓包计时。要评估公网线路收益，应结合 raw/wire 字节、连接握手次数和多轮 E2E；不能仅用本机亚毫秒发送边界推导完整对话提速。

## 执行

在 `turbo/` 目录执行：

```bash
export AI_COVE_API_KEY  # 由安全环境注入，不要把值写进命令历史或仓库
TURBO_BENCHMARK_RUNS=5 TURBO_BENCHMARK_WARMUPS=1 npm run benchmark:live
```

只读取 `AI_COVE_API_KEY`，不会修改 `~/.codex/config.toml`，也不会输出 API Key、请求正文或响应正文。可选环境变量：

```text
TURBO_BENCHMARK_UPSTREAM       默认 https://api.ai-cove.com/v1
TURBO_BENCHMARK_MODEL          默认 gpt-5.6-luna
TURBO_BENCHMARK_PROMPT         默认固定的可压缩长上下文
TURBO_BENCHMARK_RUNS           默认 5，必须大于 0
TURBO_BENCHMARK_WARMUPS        默认 1，可为 0
TURBO_BENCHMARK_TIMEOUT_SECS   默认 180，必须大于 0
```

开发验证可先用一轮正式样本：

```bash
TURBO_BENCHMARK_RUNS=1 TURBO_BENCHMARK_WARMUPS=0 npm run benchmark:live
```

长上下文和多轮场景必须观察 Turbo 的 `wire < raw`；短上下文不作这个硬性要求，因为正确的 zstd 策略可能选择原样发送，但报告会保留实际 bytes 结果。

## 报告解读

每个非直连单元格会打印相对同一使用场景直连基线的 median 比值：

- `1.00x` 表示与直连相同；
- 大于 `1.00x` 表示当前路径更快；
- 小于 `1.00x` 表示当前路径更慢。

旧版只测“一次 HTTP POST / 一条 WS 应用消息”的三行结果不再作为结论；它没有覆盖连接复用，也不能代表连续多轮会话，后续结果必须以本 3×3 输出为准。

## 2026-08-04 线上实测

参数：默认上游、默认模型、`runs=5`、`warmups=1`；API Key 只通过环境变量注入。以下为正式样本的 median/P95，单位为毫秒；速度比值为“同场景直连 median ÷ 当前路径 median”，大于 1 表示当前路径更快。

相对同场景直连的总 E2E median：

- 短上下文：Turbo HTTP `1.28x`，Turbo WS `0.65x`；短包 HTTP 未压缩，WS envelope 从 `102` 字节变为 `112` 字节。
- 长上下文：Turbo HTTP `1.15x`，Turbo WS `0.55x`；两条 Turbo 路径分别节省 `99.3%` 和 `99.2%` 请求应用字节。WS 每轮 E2E 为 `0.93x`，但单轮握手成本使总 E2E 变慢。
- 连续 5 轮：Turbo HTTP `1.16x`，Turbo WS `1.17x`；WS 只握手一次，累计 E2E 略快于 HTTP，且每轮 E2E 为 `1.35x` 的直连速度比值。

这组结果只代表本次公网时间窗和固定工作负载，不把模型响应波动归因于压缩；最稳定的收益是长上下文/多轮请求字节减少，以及多轮 WS 的握手复用。
