# AI Cove Turbo UI/UX 评审

## 结论

**建议：REVISE。** 当前版本已经形成鲜明、可信的桌面工具气质，配置与运行的职责边界也很清楚；但在进入小范围 beta 前，仍应先解决“是否真正生效不够一眼可知”、默认窗口关键动作落在首屏外、指标命名容易误读和运行页信息重复四个问题。

本轮只做评审，不修改已确认的 B/C 视觉基线。下文把建议分成两类：未特别标注的建议可在现有设计契约内实施；标注“需调整基线”的建议必须先取得产品确认，并同步修改 `DESIGN.md` 或 MVP 规格，不能直接改实现。

## 评审范围与证据

- 基线：`a324a1c`（当前 `main`）。
- 设计约束：`DESIGN.md`。
- 产品规格：`docs/specs/2026-08-03-ai-cove-turbo-mvp.md`。
- 实现：`src/index.html`、`src/styles.css`、`src/app.js`、`src-tauri/tauri.conf.json`。
- 浏览器实测：375×812、768×900、1280×900，以及原生默认窗口 1180×800。
- 375 / 768 / 1280 均无整页横向滚动；运行页没有配置动作；Tab 的点击、左右方向键、焦点、URL 和面板同步正常；控制台无 error / warning。
- 原生默认窗口 1180×800 下，配置内容区可视高度为 742px，配置卡高约 873px；“版本更新”和“重启 Codex”分别从约 849px、928px 开始，首屏不可见。
- 源码路径复核了配置阻塞、本地上游修复、非 AI Cove 确认、更新进度、关闭窗口隐藏、托盘重新打开和退出时恢复配置等关键流程。

## 做得好的地方

1. **职责边界明确。** “配置”负责动作，“运行”只读，避免在观测页面误触重启或开关。
2. **状态不只靠颜色。** 开关有“开/关”和 `aria-pressed`，Tab 有完整语义与键盘操作，等待、异常和已验证也有文字说明。
3. **品牌语言成立。** 深绿黑底、海蓝强调、网格与等宽数据形成了可识别的本地基础设施工具气质，没有落入通用 SaaS 面板。
4. **隐私边界说得清楚。** “没有正文、没有密钥、没有历史数据库”位于运行页主标题下方，符合用户最先会担心的问题。
5. **响应式策略克制。** 小宽度隐藏重复的 DETAIL 列，同时保留路线与状态，不靠整页横向滚动兜底。
6. **危险流程有明确恢复路径。** 本地回环上游提供“设置为 AI Cove”，配置阻塞提供“重试接管”；非 AI Cove 确认后警告仍持续存在，不会把一次确认伪装成兼容。
7. **桌面生命周期符合常驻工具预期。** 关闭窗口只隐藏，托盘提供“打开设置”和“退出 Turbo”，退出失败时重新显示窗口，避免静默留下未恢复的配置。

## 关键流程补充判断

- **配置缺失、损坏或冲突：** 顶部会降级为未就绪，配置区给出错误原因，并在可恢复状态提供“重试接管”；方向正确，但错误与动作反馈仍受下文“离触发位置太远”问题影响。
- **非 AI Cove 上游：** 首次需要明确确认，确认后兼容性警告继续保留；这比一次确认后永久消失更诚实。
- **关闭与退出：** 窗口关闭只隐藏，托盘退出会先恢复配置，恢复失败则重新显示窗口；行为安全，主要问题是“关闭仍在后台”的提示首屏不可见。
- **检查与安装更新：** 已有检查、发现版本、下载、安装、失败和进度语义，进度条也提供 `aria-valuenow`；但整个更新区位于默认窗口首屏之外，且失败仍回写上方统一消息。

## 优先问题

### P1：生效链路被拆散，用户不能一眼判断“现在到底有没有加速”

产品实际存在三项共同前置条件：本地服务正常、配置已接管、Codex Desktop 已重启；之后才分成两条独立能力链：HTTP zstd 的真实请求验证，以及 WebSocket 握手与公网腿 zstd 实际发送验证。当前页面把这些事实分散在顶部状态、当前配置、底部重启按钮和两项传输状态中；`restartRequired` 只改变底部按钮文案，`websocketZstdVerified` 则没有进入当前前端展示。

这会让“通道运行中”和“已接管”显得比真实生效更确定。用户尤其容易漏掉仍需重启 Codex 的状态。

**建议：** 在配置页顶部增加一条紧凑的“生效状态”：先展示 `服务 → 配置 → Codex 重启` 三项前置条件，再分别展示 `HTTP zstd` 与 `WebSocket（握手 / zstd）` 两条能力状态。只展示事实，不增加向导或新页面；需要重启时，把重启按钮提升到这条状态旁边。

### P1：默认窗口把关键恢复动作放到了首屏之外

默认窗口是 1180×800，但配置卡约 873px 高；“版本更新”和“重启 Codex”首屏不可见。配置页又采用“紧凑菜单栏弹层”的视觉隐喻，用户通常不会预期它还需要向下滚动才能完成关键动作。

**建议：** 优先删减垂直重复信息，而不是放大窗口。配置页的会话指标可以只留三项数字；两条传输状态移入上面的“生效状态”。需要重启时让 CTA 始终在首屏，更新入口可继续放底部。

### P1：`压缩率` 的名称与实际计算含义相反

后端计算的是 `(原始字节 - 已发送字节) / 原始字节`，即“节省比例”。示例中的 1.84 MB → 1.06 MB 显示 42.4%，这是节省 42.4%，不是常见语义下的“压缩后占原始大小 42.4%”。

**建议（需调整 MVP 术语基线）：** 产品先确认这里要表达“节省比例”还是“压缩后占比”。若保留当前算法，应先把规格中的“压缩率”同步改为“流量节省率”，再将界面统一为 `节省率 / SAVED / bytes saved`；数字卡可直接显示“已省 780 KB · 42.4%”。

### P2：运行页重复展示同一批状态，密度高但新增信息少

左侧路线、状态表和页脚重复了 SERVICE、CONFIG、ZSTD、WS、请求数与回退数；柱图又重复了上方 RAW / SENT 数字。当前没有时间序列，图表不能表达趋势，只是把两个总量再画一次。

**建议：** 在保留 `DESIGN.md` 已锁定的路线、指标、传输图和状态表结构下，按奥卡姆剃刀删减重复文案：

- 左侧只保留 LOCAL / UPSTREAM 和配置归属；
- 状态表保留服务、重启、HTTP zstd、WS 握手与 WS zstd 状态；
- 页脚只保留握手与回退计数；
- 传输图继续保留 RAW / SENT 对比，但不再重复上方已有的完整数字说明；在真正有时间序列前不要把它描述成趋势图。

### P2：关键辅助文字过小且低对比，影响高密度扫读

配置页部分说明为 9.6px，运行页路由标签约 8.8px、表头约 8.5px。`#5d6b64` 在 `#151c1b` 上对比度约 3.09:1，`#506057` 在 `#080c0b` 上约 2.95:1；这些内容不是纯装饰，却低于普通正文常用的 4.5:1 可读性基线。

**建议（需调整 B/C 视觉基线）：** 这是当前“完整保留旧版字号与中性色”约束带来的已知可读性代价。若 beta 前决定让可读性优先，应先修改 `DESIGN.md`，再把有语义的辅助文字统一提高到至少 11–12px，并将 `--b-faint`、`--c-faint` 提升到 4.5:1；版本号、网格标记等装饰元数据可继续更小、更淡。

### P2：动作反馈离触发位置太远

所有动作失败都只更新“当前配置”底部的同一个消息。用户在卡片底部点击“检查更新”或“重启 Codex”时，失败信息可能出现在当前视口上方；除重启外，其余按钮在 pending 时也没有明确的可见文案变化。

**建议：** 只增加一个卡片内吸顶/吸底的 `aria-live` 状态条，显示当前动作、成功或失败；不为每个按钮分别造 Toast、Dialog 或状态组件。

## 次要问题

1. **双层品牌栏占空间。** 全局壳层和 B/C 内层都重复产品名；运行页等于连续两条顶栏，小窗口尤其明显。这是当前 `TurboShellHeader` 与 B/C 保真要求的直接结果，本轮不建议改；如将来重新确认视觉基线，再评估是否合并。
2. **装饰性 `···` 像可点击菜单。** 它有 hover 反馈但没有动作和键盘语义。当前作为 B 基线保留；如将来调整基线，要么删除 hover，要么等真正有菜单时再放按钮。
3. **WebSocket zstd 的验证状态缺席。** 后端已经区分 WebSocket 握手验证和 `websocketZstdVerified`，前端目前只显示握手/连接状态，用户无法知道公网腿 zstd 是否真正发送过消息。
4. **关闭后仍在后台运行的提示不够可见。** 托盘退出与恢复逻辑是完整的，但唯一提示位于配置卡下方，在默认窗口首屏不可见；建议把“关闭窗口不会停止 Turbo”移到壳层可见区域，同时保留托盘中的明确退出命令。
5. **窄屏底部按钮只有约 31px 高。** 鼠标仍可用，但不适合触控或低精度操作；若 Windows 触控设备进入范围，再统一提升到至少 40–44px。

## 建议的最小改动顺序

1. 增加“共同前置条件 + HTTP / WS 独立验证”的生效状态，并把必要的重启 CTA 提到首屏。
2. 把“关闭窗口不会停止 Turbo”移到首屏可见区域。
3. 在保留既定结构的前提下，删除运行页重复文案，并补出 WS zstd 实际发送状态。
4. 产品确认“压缩率”术语后，先更新 MVP 规格，再改界面文案。
5. 产品确认可读性优先级后，先更新 B/C 视觉基线，再调整字号与中性色。

以上五步不需要新依赖、新页面、历史数据库或新的状态模型；现有 `AppStatus` 已包含所需字段。双层品牌栏和 `···` 不进入当前最小实施范围。
