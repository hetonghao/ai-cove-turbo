# Turbo 公平 3×3 基准

## 最新结论

这份报告取代旧 3×4 模型性能结论。旧基准让 HTTP Client 跨样本复用连接，而 WS 每个样本重新握手，不能用于判断冷启动 HTTP 与冷启动 WS 的差异。本版把每个样本定义为一个独立会话：三条路径的公网连接均从冷状态开始，连续 5 轮只在同一样本内复用。

当前可以严谨支持的结论：

1. **单轮会话优先 Turbo HTTP。** 单轮短、长上下文的 Turbo WS 总 E2E 中位数分别为 `3560.5 ms`、`4139.5 ms`，Turbo HTTP 分别为 `2097.3 ms`、`2865.7 ms`。WS 单轮多出约 `1.8 s` Upgrade/鉴权/上游协商；样本范围仍有重叠，因此这是当前环境下的产品路径结论，不是协议定律。
2. **连续 5 轮时 Turbo HTTP 与 Turbo WS 总 E2E 基本持平。** 两者为 `13687.2 ms` 与 `13567.8 ms`，WS 仅低约 `0.9%`，远小于样本波动，不能判定总 E2E 已稳定胜出。
3. **连接建立后，Turbo WS 的多轮指标更好。** warm request 中位数为 `1926.6 ms`，比 Turbo HTTP 的 `2178.3 ms` 低约 `11.6%`；TTFT 为 `985.7 ms`，比 `1539.0 ms` 低约 `36.0%`。WS 完成 `1 handshake / 5 messages / 0 reconnects`，证明收益来自真实连接复用。
4. **短报文继续不压缩。** 159-byte HTTP 保持 `159 → 159`；170-byte WS 加 10-byte AICZ envelope 后为 `170 → 180`。当前策略 `<1024 bytes` 原样发送。
5. **长报文压缩收益稳定。** 约 108 KiB 源码型输入在 HTTP、WS 两条 Turbo 路径均减少约 `78.4%` 应用负载；在 10 Mbps 假设下理论少约 `67.9 ms/请求` 的 payload 序列化时间。它不能解释秒级模型 E2E 差异。
6. **不再把纯 WS、不压缩作为模型性能场景。** 标准 WS 只保留握手与兼容性回归；付费模型基准固定为直连 HTTP、Turbo HTTP 自适应 zstd、Turbo WS 自适应 zstd。

按本轮 warm request 中位数粗算，WS 每轮约节省 `251.7 ms`，摊薄 `1775.7 ms` 的握手中位数大约需要 7 个 warm rounds。这个数字只用于选择进一步测试的轮数，不是固定产品阈值。

## 公平口径

| 项目 | 口径 |
|---|---|
| 使用场景 | 单轮短上下文、单轮长上下文、连续 5 轮固定长上下文 |
| 技术路径 | 直连 HTTP、Turbo HTTP + 自适应 zstd、Turbo WS + 自适应 zstd |
| Direct HTTP | 每个样本创建新的 reqwest Client；多轮在该 Client 内复用连接 |
| Turbo HTTP | 每个样本创建独立的临时代理状态和上游 Client；代理启动不计时，首次公网 TCP/TLS 计入首轮 E2E；多轮复用同一上游连接 |
| Turbo WS | 每个样本建立一条新的客户端与私有上游 WS；多轮在该连接内发送 |
| 采样 | `runs=12`、`warmups=1`；三路轮转，runs 必须是 3 的正整数倍 |
| 模型与输入 | `gpt-5.6-luna`；内置 `builtin-source-smoke`，98,304 bytes，FNV-1a `6fd028d239956991` |
| HTTP setup | TCP/TLS 包含在首轮和总 E2E；reqwest 不单独暴露 setup，因此不与 WS setup 列直接相减 |
| WS setup | `connect_async` 到 101 完成，包含 DNS/TCP/TLS/Upgrade/鉴权/上游协商 |
| 字节 | 仅请求应用负载，不含 headers、TLS、TCP/IP、重传或响应 |

连接生命周期由本地测试锁定：两次 Turbo HTTP 样本产生两条上游 TCP；同一样本内两轮只使用其中一条。模型运行前 focused benchmark suite 为 `31 passed / 3 ignored`。

正式命令：

```bash
unset TURBO_BENCHMARK_PROMPT TURBO_BENCHMARK_PROMPT_FILE
export TURBO_BENCHMARK_RUNS=12
export TURBO_BENCHMARK_WARMUPS=1
export TURBO_BENCHMARK_MODEL=gpt-5.6-luna
npm run benchmark:live
```

安全环境中的 `AI_COVE_API_KEY` 仅从环境读取，未输出。正式测试结果为 `1 passed / 0 failed`，耗时 `876.58 s`。

## 生产 Transport ACK（独立路径证据）

发布 `v1.0.0-rc.23` 后，生产 `/v1/transport/ack` 的四条路径均通过。该测试使用固定 67,257-byte 高可压缩夹具，不调用模型；`AI_COVE_API_KEY` 仅从安全环境读取，未写入输出。

```bash
TURBO_TRANSPORT_ACK_UPSTREAM=https://api.ai-cove.com/v1 \
TURBO_TRANSPORT_ACK_ALLOW_PRODUCTION=1 \
  cargo test --manifest-path src-tauri/Cargo.toml \
  live_transport_ack_benchmark -- --ignored --nocapture
```

| 路径 | client ACK RTT | WS setup | 服务端 receive | 服务端 decode | wire → decoded bytes |
|---|---:|---:|---:|---:|---:|
| Direct HTTP | `1945.204 ms` | — | `143.337 ms` | `0.134 ms` | `67257 → 67257` |
| Turbo HTTP + zstd | `1620.274 ms` | — | `0.005 ms` | `0.140 ms` | `102 → 67257` |
| Direct WS | `903.112 ms` | `1645.924 ms` | `903.723 ms` | `0.000 ms` | `67257 → 67257` |
| Turbo WS + zstd | `359.506 ms` | `1699.959 ms` | `362.980 ms` | `0.107 ms` | `112 → 67257` |

这一次观测支持但不扩大模型基准结论：

1. **压缩路径在生产真实生效。** HTTP、WS 的 wire payload 分别降至 102、112 bytes，服务端解码仅增加约 `0.1 ms`。这里约 `99.8%` 的缩减来自重复型门禁夹具，只证明协议链路；源码型模型负载仍以正式 3×3 的约 `78.4%` 为准。
2. **WS 冷启动成本被独立复现。** Direct、Turbo WS setup 分别约 `1.65 s`、`1.70 s`。简单相加后首个 ACK 为约 `2.55 s`、`2.06 s`，不能拿不含 setup 的 WS ACK RTT 当用户冷启动延迟。
3. **单次 ACK 不能证明稳定提速。** 本次 Turbo HTTP RTT 比 Direct HTTP 低约 `16.7%`，Turbo WS 建连后的 ACK RTT 低约 `60.2%`；但没有重复样本和分布，只能用于确认上传、解码和握手路径，不能替代模型 E2E/TTFT 基准。
4. **产品选择保持不变。** 冷启动完整会话优先 HTTP；连接已经建立且会连续复用时，WS 才可能逐步摊薄 setup。ACK RTT 是往返时间，不是单向纯传输时间。

## 边界

- 这是当前产品路径的公网模型观测，不是 HTTP 与 WS 协议的实验室定理。
- 模型排队、推理、提示缓存和公网波动仍占主要部分；样本范围大幅重叠时不判定因果胜负。
- WS TTFT 不含 setup；用户从会话开始等待首事件时，必须同时考虑 setup。
- 5 轮结果不能证明第 6、7 或更多轮必然更快；下一次需要寻找 break-even 时，应固定相同版本后增加轮数梯度，而不是恢复纯 WS 路径。
- ACK RTT、压缩 CPU、10 Mbps 理论 payload 时间与模型 E2E 是四种不同证据，继续分开报告。
